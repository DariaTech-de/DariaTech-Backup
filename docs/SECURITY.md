# Security model and current limits

## Implemented

- Console enforces HTTPS in Production except health probes. Reverse proxy headers are trusted only from explicit proxy addresses. Caddy manages certificates; PostgreSQL is not publicly exposed.
- Administrator/operator and future customer roles are distinct from device identities. Customer roles have mandatory tenant claims; queries are scoped and composite foreign keys prohibit cross-tenant parent relationships. Cross-tenant lookups return 404. Internal MSP notes are omitted from customer API/export results.
- Passwords use ASP.NET Identity V3 PBKDF2-HMAC-SHA512, 210,000 iterations, random salts. Mandatory RFC 6238 TOTP has a persisted consumed step, preventing code replay. Account attempts and step consumption are serialized in PostgreSQL; five failures lock the account for 30 minutes. IP limits also cover login and enrollment.
- Cookies are HttpOnly, SameSite=Strict and Secure in Production; fixed 30-minute sessions. Database session versions revoke disabled/changed accounts. Forms and management API mutations require antiforgery tokens. Agent routes do not accept cookies as device credentials.
- Random 256-bit enrollment tokens are stored as SHA-256 hashes and redeemed atomically once, with expiry and fixed tenant/site. Device credentials are independently generated and stored as hashes. Revocation denies further telemetry.
- AES-256-GCM encrypts management secrets with tenant/purpose associated data. ASP.NET Data Protection XML keys are encrypted by the same external master key. Store master key separately from database/key volume backups. Never lose it: TOTP secrets and sessions cannot be recovered without it. A future Vault implementation can replace ISecretStore.
- Windows agent identity/engine credential/outbox use DPAPI CurrentUser under the service account. Unix uses an explicit external 256-bit key and restrictive directory/file permissions. Console traffic requires HTTPS; engine traffic is authenticated and loopback-only. Redirects are disabled, avoiding credential redirection.
- Typed telemetry excludes paths, destinations, options, passphrases, raw logs and exception strings. Allowed error codes are BackupFailed/BackupWarning/EngineUnavailable/Cancelled/EngineOperationFailed. Unknown operation statistics remain null. Statistics are bounded/validated; terminal runs are immutable and deduplicated.
- Self-hosted UI assets, output encoding, CSP, frame denial, nosniff, referrer policy and HSTS. No external scripts/analytics. Input sizes and request body size are bounded.
- Audit events record login outcomes, provisioning, enrollment, customer/site/storage changes, device revocation, logout and exports. A PostgreSQL trigger rejects audit UPDATE/DELETE. The running web app has no migration/superuser credentials.

## Explicit release gaps

Remote backup/restore/configuration/update APIs do NOT exist yet. No untrusted command can be executed by this implementation. Design requirement for those phases: allowlisted typed commands, role checks and tenant-bound authorization, signature, device audience, command ID, expiry, persisted single-use execution receipt, audit record and an extra restore approval. Signing alone does not prevent replay. Arbitrary shell execution and arbitrary engine API forwarding are prohibited.

Local maintenance-only MFA/password recovery and retained-key decryption are implemented below. Recovery codes, a distributed session inventory, production penetration testing and automatic key retirement remain outstanding. Bootstrap uses a protected local password file and writes a one-time TOTP provisioning file, which must be deleted after enrollment. Windows CI now verifies SYSTEM service provisioning, DPAPI isolation, restrictive ACLs, rejection of insecure pre-existing state, upgrade/restart/uninstall and authenticated telemetry. Authenticode signing, VSS, reboot recovery and customer-specific Windows validation remain release gates. UI administration of roles is limited to the implemented actions; do not claim a customer portal is production-ready merely because scoped roles pass tests.

EF query filters are defense in the application, not PostgreSQL row-level security. IgnoreQueryFilters is limited to token redemption and device authentication with subsequent scope assignment. Raw SQL/schema owner access bypasses application tenant protection; do not give application credentials to customer users. Audit append-only behavior is not an externally notarized tamper-proof ledger; database owners can change triggers.

Secrets never belong in repository, SMTP test output or ordinary logs. Keep Include Error Detail=false and EF sensitive-data logging disabled. Run dependency audits, security integration tests, actual restore tests and a PostgreSQL disaster-recovery drill before production.

## Data protection / DSGVO

Collect hostname, OS/version, contact timestamps, numeric backup statistics and required customer contact data. IP addresses and raw engine logs are not centrally collected. Explicit managed policies and authorized restore catalog requests contain source/file paths; these are encrypted, access-controlled and audited. Process backup metadata under the customer's documented agreement; choose EU storage/hosting and document processors. Export is tenant-scoped; current API caps run export at 10,000 and explicitly reports truncation.

Device removal currently revokes credentials and archives the device; it is NOT physical erasure. Use the owner-only maintenance erasure and history retention procedures below; erasure requires an archived customer and revoked/inactive devices. Preserve required pseudonymized audit evidence and retention obligations. Retain engine/storage backups according to customer policy independently. Do not silently prune backup versions or audit records.

### Managed device presentation

`branding/product.json` sets `managedAgentUI` for the DariaTech local UI. In that profile, vendor remote-registration/update-channel controls and engine access controls are not offered in Settings; the managed Windows service supplies the loopback binding and protected engine credentials. Hiding UI controls does not implement API authorization or disable the underlying upstream endpoints. The engine API remains a local authenticated administrator surface. Central signed commands and approved updates are implemented behind explicit local trust settings. Visual settings pages are handled separately and are not the authoritative feature inventory. Original engine/license credits remain accessible in About and Open Source.

Managed configuration is an explicit privileged trust decision on each agent, disabled by default. Console writes require Admin + mandatory MFA session + CSRF. The entire configuration is purpose/tenant/revision-bound AES-GCM encrypted, and management GETs exclude configuration/secrets. Delivery requires matching device identity and credential, active enrollment, active customer and tenant scope; compound foreign keys protect relationships. Application and PostgreSQL triggers reject revision modification and ordinary deletion; only deliberate owner-authorized tenant erasure permits deletion. The agent rejects rollbacks/mutations and arbitrary options, does not remotely accept scripts/custom modules or keyfile paths, and reconciles only engine jobs carrying its stable managed identity. Central admin source selection can expose files to the specified backup target: restrict administrative rights and review policies before enabling this feature.

Remote operations require a separately pinned agent public key, local opt-in and a managed engine. The Console private signing key must remain on a protected read-only secret mount. Keep it separate from offline update signing keys. Signatures include UUID, device, tenant, operation, job, parameters and expiry. Agent write-ahead journals make uncertain dispatch visible without retrying side effects. Managed engine boot identities prevent in-memory task ID reuse from producing false completion. Remote restore is restricted to newly created directories under a local RestoreRoot, with overwrite disabled and a second administrator's approval required. A command is not a remote shell or arbitrary API proxy.

Update trust is independent from command-signing trust. The update private key is offline; Console approval never signs arbitrary uploaded executables. Agent update payloads require offline signatures, approved device assignment, valid expiry, strictly increasing accepted sequence, newer actual installed version, a permitted HTTPS host chain, exact size/hash and matching Windows installer file version. Locally protected journals preserve anti-rollback state. Staged binaries are rehashed before execution and active/queued engine work defers updates. Failed/uncertain installers are not automatically retried or downgraded. Authenticode signing and interrupted-installation recovery remain explicit production rollout checks.

## Master-key rotation and emergency administrator recovery

New Console secret envelopes identify the active master key (`v2:key-id:ciphertext`). Existing original AES-GCM envelopes remain readable. Configure `Security:LegacyMasterKeyFiles` with a comma-separated protected list (maximum 16) when switching to a newly generated 256-bit master key. Existing TOTP/storage/configuration/command/SMTP/data-protection secrets continue to authenticate against retained keys; new writes use the active key only. Tenant/purpose binding and authentication remain mandatory for every key. Key identifiers are hashes, not secret key material. Keys/plaintext buffers are cleared on disposal where possible.

Stop/restart the Console for a controlled rotation, back up database **and all key files**, mount current/retained files read-only and verify login plus encrypted records before removing the previous deployment. Keep legacy keys until all old database revisions, SMTP envelopes and encrypted data-protection XML (including retained backups) have been migrated or retired. This is rolling key rotation, not automatic destruction of all historical key material. Never overwrite master.key without retaining the previous key; doing so loses access to encrypted records. Do not rewrite immutable revision rows to rotate a key.

If an authenticator is lost or exposed, use the local maintenance-only `--recover-user` mode with Provision:Email, a protected replacement PasswordFile (14–200 characters) and a new TotpOutputFile. It rotates both password/TOTP, unlocks the account, revokes existing sessions, resets the TOTP replay counter and appends `user.credentials-recovered` to the audit log. It cannot reactivate inactive users/customers and refuses overwriting an existing secret output file. There is no anonymous web recovery endpoint or MFA bypass. Access to the host, maintenance database credential and encryption key is the recovery authority; protect it separately from technician accounts. Register the replacement secret through a trusted channel and immediately delete plaintext provisioning files.

## Retention and deliberate customer erasure

Local maintenance CLI `--prune-history` is dry-run by default. `Privacy:RetentionDays` accepts 30–3650 days (default 180); deliberate `Privacy:Apply=true` prunes completed/terminal old run records, old terminal delivery records, expired enrollment tokens, old terminal/never-dispatched expired commands (including encrypted catalogs) and resolved alerts without remaining delivery references. Pending deliveries, running runs and accepted engine commands are retained; audit events are not silently pruned. Count summaries are emitted without customer names or secrets. The migration/table-owner connection is required for applying maintenance; the ordinary Console application role is denied.

`--erase-customer` requires `Privacy:TenantId`, a previously archived customer and revoked/inactive devices. It is dry-run unless Privacy:Apply=true. Deliberate erasure removes central configurations including encrypted revisions, commands, devices/jobs/runs, enrollment credentials, storage credentials, notification recipients/deliveries, sites and customer contact data in one transaction. Customer user accounts are anonymized, disabled and sessions revoked. Append-only audit IDs and a pseudonymous tenant tombstone remain to record the deletion. A narrowly scoped PostgreSQL trigger exception allows revision DELETE only for the table owner and the matching transaction-local erasure tenant; the application role cannot enable that exception. Ordinary configuration updates/deletes remain blocked.

Central erasure does not delete backup archives on customer storage, agent-local encrypted databases, mail already delivered or older operational database backups. Those copies follow the separately agreed customer/storage/database-backup retention and disposal procedures. Do not claim immediate removal from all copies. Complete the customer contract's backup disposal separately; revocation prevents future Console access/enrollment. Already delivered short-lived commands cannot be retroactively removed from an executing engine; disable the local agent for immediate offboarding control.

### Local managed engine connection ownership

Managed Windows agents validate the kernel's server-side TCP connection owner and process creation time against the protected identity of their launched engine, before sending any HTTP data or engine credentials. Connections to a foreign loopback listener fail closed; PID reuse and restarts invalidate old identities. The guard runs for each newly established connection, not merely once when checking whether a port is free. Existing unmanaged engine connections are an explicit local trust mode and do not gain this managed-child verification. The local `--check-engine-port PID START_UTC_TICKS PORT` diagnostic sends no credentials or HTTP payload.
